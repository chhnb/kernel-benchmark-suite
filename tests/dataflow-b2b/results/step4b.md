# 第 4b 步 DCT8 性能诊断与 PCM32 端到端验证

## DCT8

复用第 4a 步的 HSACO、4096 × 4096 输入、8 × 8 线程块和 Radeon VII（gfx906）。每个版本完成一次 rocprof 采集，包含 3 次预热和 15 次记录。计数按后 15 次的中位数报告。

### 最终机器指令

访存列含 SMEM 和 VMEM。SALU 单列标量算术、掩码更新及地址运算。分支和 `s_waitcnt`、`s_barrier`、`s_endpgm` 分别计数。地址来自最终 HSACO 的反汇编。

|---|---:|---:|---:|---:|---:|

| anchor 第一臂 `0x19a0–0x19ec` | 16 | 0 | 0 | 0 | 0 |
| anchor 第二次分支 `0x19f0–0x19f8` | 0 | 2 | 0 | 1 | 0 |

两条分支臂各自包含一套整数除法降级序列。融合后只有一套，在除法前选择被除数，随后恢复结果符号。机器码从 71 条减少到 48 条。2 条 scalar load、2 条 vector load、1 条 vector store 和 1 条 barrier 都仍存在。后端把融合版的 barrier 排到量化运算之前，并合并了等待。

`VALUInsts` 和 `SALUInsts` 分别用对应 SQ 指令计数除以 `SQ_WAVES`。动态合计少了 **4,980,736 条 wave 级 ALU 指令**，其中 3,670,016 条 VALU、1,310,720 条 SALU。分支和等待序列的减少见静态表。当前 ROCm 6.3.3 的 gfx906 指标表没有可用的动态驻留率，采集 `SQ_WAVE_CYCLES` 会被拒绝。表中的驻留值来自 HIP occupancy API，只是资源上限。[AMD rocprof 文档](https://rocm.docs.amd.com/projects/rocprofiler/en/docs-6.4.1/how-to/using-rocprof.html)

静态 TTI 的 29% 降幅确有机器指令收益，且 VALU 忙碌率下降。量化路径仍依赖输入和量化表读取、一次除法链及输出写回。访存指令、寄存器占用（12 VGPR、16 SGPR）和驻留上限保持一致，访存停顿未随 ALU 指令数下降。第 4a 步非采集计时和本步采集计时都只相差约 0.02%。这些证据表明减少的 ALU 工作没有支配端到端时间。现有计数不足以区分访存延迟、同步及其他隐藏延迟各自的贡献。

## PCM32

冻结 kernel 输入为 `db3b35287f1ef284e3c8dac514b05fc952a6892345b5ff0077b2840927aaab47`，函数为 `_Z3pcmPi`。使用原 32,768 × 32 线程布局、每组 8,192 个整数。四个变体各自用 CPU 对每组排序，逐元素复核冻结参考，再将 GPU 的 268,435,456 个输出与该参考逐字节比较。所有计时和采集发射也核对全量输出。

正式 PCM32 搜索中，dataflow-exact 的 51 条尝试包含 33 个参考求解器候选、1 个原有 anchor 生成、1 个原有 R2R 生成和 16 个仅归一化尝试。没有候选触发规模回退。对同一个 PCM32 菱形添加两侧各四条运算后，12 条的隔离对照触发回退，anchor 与 dataflow-exact 的布局、裁决和清理后 IR 均一致，清理后 TTI 为 1379。该诊断输入不参与下列 PCM32 性能结果。

同一 Radeon VII 上每版一次成功采集，包含 3 次预热和 15 次记录。动态 wave 驻留率在 gfx906 的这套 rocprof 中无可用指标。三版静态驻留限制为每 CU 一个 workgroup，每个 workgroup 只含一个 wave64。

反汇编中，anchor 和 DARM 各 355 VALU、77 SALU，dataflow-exact 为 352 VALU、76 SALU。三版均有 101 条访存指令、21 条分支和 58 条等待、同步或结束指令。各机器基本块和逐次采集数据见证据 JSON。

dataflow-exact 每个 wave 少执行 1,536 条 VALU 和 512 条 SALU。三版均使用 64 KiB LDS、28 个 VGPR 和 32 个 SGPR。访存忙碌率、访存停顿和驻留上限接近或相同。计数器采集重现了正式计时中约 0.47% 的耗时增加，当前数据无法定位造成这段差距的指令依赖或等待。
