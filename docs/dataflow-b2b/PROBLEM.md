# 分支区域融合：问题定义（第二版）

## 0. 一句话

给定一个分支区域，在左右两侧之间选出配对和操作数的对应关系，再把配对结果生成为代码，
使区域局部清理之后的执行代价在分歧和一致两类场景下都尽量低。

## 1. 区域与边界

条件 $C$ 把区域分为两侧：满足 $C$ 的线程执行左侧 $A_L$，其余线程执行右侧 $A_R$，两侧在汇合块 $J$ 合流。
第一版只考虑 B2B：两侧各是一个直线基本块，或者其中一侧为空（三角形）。

区域有两个边界：

- **入口（entry）**：区域外定义的值，包括分支前的值、参数、常量，记为 $E$。它们对两侧都可用，两侧相同。
- **出口（exit）**：区域必须交付的结果，包括：
  - **输出值对** $O$：$J$ 中每个 PHI 的两侧入值 $(a, b)$，含义是满足 $C$ 的线程得到 $a$，否则得到 $b$；
  - **副作用**：每侧的 store 等必须保持的效应，以及它们之间的先后顺序。

每侧的依赖图 $G_s = (I_s, E_s)$：$I_s$ 是该侧的操作，$E_s$ 是数据依赖和必须保持的副作用顺序。

## 2. 基本概念

- **值对** $(a, b)$：$a$ 是左侧的值或入口值，$b$ 是右侧的值或入口值。
- **相同值对** $(e, e)$：同一个入口值。不需要任何代价。
- **合并值** $m_{lr}$：左侧操作 $l$ 和右侧操作 $r$ 合并后的结果。在左侧线程上等于 $l$，在右侧线程上等于 $r$。

## 3. 问题一：配对

### 3.1 决策

1. **配对** $\pi$：左侧每个操作要么配给右侧一个操作，要么不配。配对一对一。
2. **操作数对应** $\sigma$：每个配对 $(l, r)$ 的第 $k$ 个操作数对应 $r$ 的哪个操作数。
   按原位置对应、可交换运算交换后对应、比较谓词互为交换时交换后对应，是第一版允许的对应方式。

### 3.2 兼容条件

两个操作可以配对，当且仅当：

- opcode 和结果类型相同；
- 内建函数调用：同一函数，常量参数相同；
- 比较：谓词相同或互为交换；
- load/store：访问类型、地址空间相同，都不是 volatile 或 atomic；
- GEP：元素类型和下标个数相同；
- 都不是跨线程操作（归约、shuffle、barrier、convergent 调用）。

### 3.3 产出集合与需求集合

$$
P(\pi) = \{(l, r) : l \text{ 与 } r \text{ 配对}\} \cup \{(e, e) : e \in E\}
$$

$$
D(\pi, \sigma) = O \;\cup\; \{(x_k, y_{\sigma(k)}) : (l, r) \text{ 配对},\ x_k = \mathrm{op}_k(l),\ y_{\sigma(k)} = \mathrm{op}_{\sigma(k)}(r)\}
$$

- 没有配对的操作不产生需求：它只在本侧线程上使用输入，直接用该输入在本侧的值即可。
  如果那个输入已经被合并，合并值在本侧线程上也是正确的。
- 配对的 store 和 load 同样产生需求：地址对和值对。这样，副作用也进入了同一套需求机制。

**需求中没有被产出的值对** $D \setminus P$（不含相同值对），每一对需要在生成阶段用一次选择来实现，
同一对只实现一次。

### 3.4 合法性

- 合并后的依赖图（包括数据依赖和副作用顺序）无环。配对之间不要求保持两侧原来的先后顺序。
- 合并的访存操作，每个线程仍只访问一次，地址和值按需求集合给出。

### 3.5 正向与反向分析（用于引导配对）

- **正向（从入口往下）**：一对候选 $(l, r)$ 的输入对中，有多少是相同值对，或可以由上游候选产出。
  越多，合并越便宜。
- **反向（从出口往上）**：一对候选产出的值对，是否属于输出值对，或者是下游候选的输入所需要的。
  不被任何需求用到的配对，只能省一次操作的代价，它的输入还可能产生新的选择。

这两个分析只用于给候选排序和剪枝。一个配对方案的真实代价按第 5 节整体计算，因为单个配对的价值依赖其他配对，
不能逐对相加。

**例**（PCM32 中的一个菱形）：

```
左：store v1 → p；  a = u - 1
右：store v2 → p；  b = w - 1
输出值对：(w, b)，(a, u)
```

两条减法合并产出 $(a, b)$，但没有任何需求等于 $(a, b)$（输出是交叉的），合并只省一条减法，
又为输入 $(u, w)$ 增加一次选择，净收益为零。两条 store 合并：地址是相同值，只有值对 $(v_1, v_2)$
需要一次选择，省掉一条 store。正向分析只看输入，会认为减法值得合并；反向分析可以看出它没有用。

## 4. 问题二：生成

给定 $(\pi, \sigma)$，产出集合和需求集合已经确定。生成阶段决定：

1. **配对的操作**：合并后只保留两侧都有的标志（例如一侧有 nsw、另一侧没有，合并后不带 nsw），元数据取交集。
2. **未满足的需求** $D \setminus P$：每一对用一个选择实现，同一对只建一次。
   代价按局部折叠后计算：两边相同为 0；常量对、i1 值对可以折叠为条件本身或简单运算；同条件嵌套的选择合并。
3. **没配对的操作**：推测执行，或者只在本侧执行（保护）。
   - 有副作用或不能安全推测的操作只能保护；
   - **满足 SimplifyCFG 推测条件的保护段，一定会被推测**（见第 6 节），所以对这样的段，保护不是一个真实的选项。
4. **执行顺序**：合并后依赖图的任意拓扑序。执行顺序中连续、同侧的保护操作组成一个保护段；
   左右各一段可以放进同一个菱形，只用一次分支。
5. **流出**：保护段中的值在段外被使用时，需要在段尾流出。
6. **输出**：每个输出值对，用产出的合并值、相同值，或一个选择来实现。

## 5. 代价

一个操作在三种场景下是否计费，取决于它的执行方式：

| 执行方式 | 分歧 $D$ | 全左 $L$ | 全右 $R$ |
|---|---|---|---|
| 所有线程执行：合并的操作、推测执行、选择 | 计 | 计 | 计 |
| 只在左侧执行（左保护） | 计 | 计 | 不计 |
| 只在右侧执行（右保护） | 计 | 不计 | 计 |

另外：每个保留下来的保护段（同一菱形的左右两段算一个）在三种场景下都计固定的控制开销；每个流出值计一次合流开销。

于是，场景 $\omega$ 下的代价为：

$$
T_\omega = \sum_{\text{配对}} c + \sum_{\text{在 } \omega \text{ 中执行的未配对操作}} c + \sum_{(a,b) \in D \setminus P} \kappa(a, b) + \text{保护段控制开销} + \text{流出开销}
$$

其中 $\kappa(a, b)$ 是值对 $(a, b)$ 的选择在局部折叠后的代价。

原始区域也按同一套规则计价，包括第 6 节的强制推测：如果原始菱形本身满足推测条件，基准就是推测后的形态。

## 6. 清理的建模

融合后的代码会经过固定的清理流程：SimplifyCFG（运行到不动点，关闭条件分支简化、公共指令上提和下沉，
两入口 PHI 折叠阈值为 7），然后 EarlyCSE、DCE、InstCombine 各一次。

原则：**只依赖区域内代码的清理效果写进模型；依赖区域外代码的效果不进模型，作为偏差测量。**

| 效果 | 来源 | 放在哪里 |
|---|---|---|
| 满足条件的保护段被推测执行 | SimplifyCFG | 生成阶段的**强制规则** |
| 两侧结构完全相同的计算合并为一个 | EarlyCSE | 配对阶段：视为已配对、没有任何需求的配对 |
| 相同的选择只保留一个 | EarlyCSE | 生成阶段：同一值对只建一个选择 |
| 选择的局部折叠 | InstCombine | 生成阶段：代价函数 $\kappa$ |
| `select(C, a op x, b op x)` 改写为 `op(select(C, a, b), x)` | InstCombine | 配对阶段：视为配对 |
| 没有使用者的值被删除 | DCE | 不需要建模：生成只产生需要的操作 |
| 与区域外已有计算合并；涉及区域外使用者的多指令改写 | EarlyCSE、InstCombine | 不进模型，计入偏差 $\varepsilon$ |

**SimplifyCFG 的推测条件**：保护段 $g$ 被推测执行，当且仅当

1. 段内操作全部可以安全推测；
2. 段内操作的 SizeAndLatency 代价累计不超过 7（第一条操作可以单独超出）；
3. 汇合处的 PHI 不超过 3 个；
4. i1 类型 PHI 的入值不是二元运算。

推测判断按**生成时**的代码计算：清理流程中 InstCombine 在 SimplifyCFG 之后只运行一次，之后不再运行 SimplifyCFG。

**规范闭包**：配对阶段的两条规则（结构相同的计算、可由 InstCombine 合成的模式）意味着，
任何会被清理流程自动合并的情况，在模型里都必须算作配对。否则模型的预测会和清理后的实际结果不一致。

**一致性检查**：对生成的代码再运行一遍清理流程，区域内的代码应当不变。
有变化就说明模型漏了某个区域内的清理效果，从差异中可以直接看出是哪一条。

## 7. 目标

### 7.1 模型的输出

对每个方案，模型给出三场景代价向量 $(T_D, T_L, T_R)$。对一个区域，模型的结果是这些向量的 Pareto 前沿，
原始区域始终是候选之一。

### 7.2 选择策略（模型之外单独一层）

从前沿中选一个方案的规则，由条件来源决定：

| 条件来源 | 策略 |
|---|---|
| 只依赖线程号和参数 | 取 $T_D$ 最小 |
| 数据相关 | 在 $T_L$、$T_R$ 都不比原始区域差的方案中，取 $T_D$ 最小 |
| 工作组一致 | 取 $\max(T_L, T_R)$ 最小 |

如果已知 wave 层面的场景概率 $p_D, p_L, p_R$（例如来自运行时剖析），则取期望代价最小。
注意：这里的概率是 wave 层面的事件概率，分支在线程层面的走向比例无法确定它们。

## 8. 两阶段求解及其耦合

配对决定产出集合和需求集合，生成决定这些集合怎么实现。两者不完全独立：

- 配上一条操作可能把两段保护连成一段，这一收益要排好执行顺序之后才知道；
- 一个需求对如果能折叠，它的实际代价比一个完整的选择低。

做法：配对阶段用第 5 节的式子评估方案，其中选择按折叠后的最低代价计，保护段用下界估计；
对最好的若干个配对方案分别做精确的生成，取最终代价最低的。
在小区域上用完备枚举检验这个做法会不会错过真正的最优解。

## 9. 合法性

1. 合并后的依赖图无环，副作用顺序保持。
2. 推测执行不能引入立即未定义行为（除零、非法访问）。结果中的 poison 在被观察之前被选择屏蔽是允许的。
3. 最终需要正确观察某个结果的线程，必须得到正确的值。
4. 跨线程操作不能配对，也不能推测执行。

## 10. 有限性

- 每个操作恰好一种处理：配对或不配对，不允许复制；
- 操作数对应方式有限；
- 选择只为需求中的值对建立，同一对只建一次。

## 11. 前提假设

1. **单区域**：模型只处理一个区域。真实流程在整个 kernel 上反复融合，区域最优之和不一定是整体最优；
   跨区域、跨步骤的相互作用不在范围内。由前几步融合产生的区域，其"最优"以前面的融合结果为前提。
2. **输入已清理**：区域在融合前已经过同一清理流程，处于规范形式（例如比较谓词已规范化）。
3. **静态代价是代理**：模型优化的是静态代价（先用抽象代价表，再用 TTI 报价）。
   我们假设静态代价的排序与运行时间的排序一致；这一假设需要用 GPU 实测单独检验。

## 12. 暂不纳入的扩展

- 比较取反后的极性及其解码；
- 单侧补单位元（如 `x*2` 对 `x` 合成 `x * sel(C, 2, 1)`）；
- 加减互转（如 `a+b` 对 `a-b`）；
- 复制或重算（一个操作参与多个配对）；
- B2R、R2R 等多块区域；
- 多指令的整体代数重构。

## 13. 评价

- 小区域：完备枚举得到真值，用来检验两阶段求解；
- 中区域：精确求解器，与小区域的枚举结果互相校验；
- 大区域：快速算法，在小、中区域上用精确解衡量它的质量；
- 在同一批区域上对照原始区域、anchor、DARM，并报告偏差 $\varepsilon$ 和一致性检查的结果。
